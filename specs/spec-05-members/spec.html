Key RGPD & lifecycle rules (decisiones.md & §5.4)

  • Audience mapping on /api/v1/users and /api/v1/users/{id}:
  • anonymous: 401 on private; /api/v1/public/members returns only status = active && consent.publicProfile == true && !isMinor with {id, name, lastNames, nickname, aboutMe, avatar, orgRoles} and Cache-Control: public, max-age=300.
  • member: 403 on GET /users; 404 on GET /users/{id} for any other user (§10.1.2; own data is accessed via /me).
  • technical: 200 on GET /users and GET /users/{id} mapped strictly to UserStaff (fields of level public, members, staff: includes status, membershipType, joinedAt, heightCm, isMinor, emergencyContact, orgRoles, positions; excludes board/self fields such as birthDate, documentId, email, phoneNumber, address, memberNumber, leftAt, sizes, guardians, consent, account, notes). 403 on all writes.
  • board: full UserBoard read + CRUD (POST/PATCH/DELETE /users*, avatar upload); 403 on /users/{id}/account*, /anonymize, and ?hard=true.
  • admin: full UserBoard + account management + anonymize + ?hard=true.
  • Minors: isMinor is computed dynamically against today's date in Europe/Madrid (false if birthDate == null). When isMinor == true, guardians must contain ≥ 1 guardian (422 validation_failed). Minors NEVER appear in /api/v1/public/members even if consent.publicProfile == true.
  • Soft delete (DELETE /api/v1/users/{id}, decisiones.md): sets users.status = 'deleted', removes the user from org_role_holders, and automatically disables their account (user_accounts.status = 'disabled' + revokes all their active sessions + invalidates session cache). Personal data, documents, and attendance remain intact in case the person returns. Cannot soft-delete the last active admin (409 / 422). ?hard=true (admin only) physically deletes the user unless blocked by documents ON DELETE RESTRICT (409 in_use) or last-admin guard.
  • Anonymize (POST /api/v1/users/{id}/anonymize, admin only, decisiones.md): requires {"confirm": true} (422 otherwise) and rejects if target is the last active admin. In one transaction: wipes identifiable PII (name = "Persona eliminada", clears lastNames, nickname, birthDate, documentId, email, phoneNumber, address_*, aboutMe, avatar_file_id, member_number, emergency_contact_*, notes, resets consent_* = 0), sets status = 'deleted', deletes user_guardians, user_accounts, google_identities, sessions (+ cache invalidation), removes from org_role_holders, sets positions.user_id = NULL, and deletes avatar blobs post-commit — while keeping the users row, its documents, and its attendance records for historical integrity.
  • Last-admin protection: PATCH /users/{id}/account, DELETE /users/{id}/account, DELETE /users/{id}, and anonymize must prevent removing/disabling the last active admin account (409 / 422).

Sections

Filters and `isMinor` SQL calculation

Contents

GET /api/v1/users supports page, perPage, status (defaults to excluding deleted unless explicitly filtered), membershipType, isMinor (bool), orgRoleId, areaId, hasAccount (bool), q (search in name, last_names, nickname), and sort (name, memberNumber, joinedAt, createdAt; default name).

Behavior

Compute the 18-year cutoff LocalDate in Europe/Madrid (today.minusYears(18)): a user is minor iff birth_date IS NOT NULL AND birth_date > :cutoffIsoDate.

Admin account lifecycle & WhatsApp invite (§4.1 & §7.4)

Contents

POST /users/{id}/account creates an invited account (loginEmail lowercased, unique → 409 duplicate). DELETE /users/{id}/account/google deletes google_identities, revokes all sessions, and resets status to invited. PATCH /users/{id}/account updates role, status, or loginEmail (disabling revokes all sessions immediately).

Behavior

After inviting a member in the Accés tab, display a «Avisa per WhatsApp» action opening https://wa.me/<e164WithoutPlus>?text=<urlEncoded> with «Ja pots entrar a https://admin.muixerangadelx.com amb el teu compte de Google (<loginEmail>).»

Soft-delete vs Anonymize (`decisiones.md`)

Contents

DELETE /users/{id} is a reversible member deactivation (status = deleted, holders cleared, account disabled, sessions revoked, data kept). POST /users/{id}/anonymize is an irreversible RGPD erasure (confirm: true) that strips PII, guardians, account, Google link, sessions, holders, positions (user_id = NULL), and avatar files while retaining the users row (name = "Persona eliminada", status = deleted), documents, and attendance.

Behavior

In the UI, anonymize is accessible only to admin behind an explicit double-confirmation dialog warning that the operation is irreversible.
