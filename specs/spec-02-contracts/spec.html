Key business rules (§5.7 & decisiones.md)

  • Strictly board and admin only (anonymous → 401; member and technical → 403 on every /contracts* endpoint; never exposed in /public/*).
  • State progression: normal pipeline to_contact → contacted → proposal_sent → negotiating → confirmed → done → invoiced → paid. Direct jumps forward/backward or to discarded allowed via PATCH. Transitioning to invoiced auto-fills billing.invoicedAt = today (Europe/Madrid) if missing; transitioning to paid auto-fills billing.paidAt = today if missing; transitioning to discarded requires non-blank discardReason (422).
  • POST /api/v1/contracts/{id}/advance: requires {"version": N} (409 version_conflict on mismatch), advances to the next normal state (applying invoicedAt/paidAt auto-fill), and rejects already-final states (paid, discarded) with 422 validation_failed.
  • Overdue calculation: overdue = (nextActionAt != null && nextActionAt < today(Europe/Madrid) && status !in {paid, discarded} && !archived).
  • Diputació catalog tracking (GET /api/v1/contracts/summary?year=): counts non-archived type = dipu_catalog contracts whose reference year (performanceDate in Madrid TZ, falling back to updatedAt if null) equals year (default current year): total = non-discarded count, confirmed = status in {confirmed, done, invoiced, paid}, limit = EnvConfig.dipuCatalogLimit (default 5). Server never blocks exceeding limit; webapp prompts confirmation before confirming or advancing into confirmed when confirmed >= limit.
  • POST /api/v1/contracts/{id}/create-event (decisiones.md): if eventId != null → 409 already_exists. Uses contract.performanceDate as Event.date; if performanceDate == null, requires date (and optional endDate, allDay) in the request JSON body (otherwise 422 validation_failed). Creates an Event (name = contract.title, category = actuacio, type = actuacio, status = confirmed if contract is confirmed+ else planned, published = false, locationName = client.municipality, address = client.address, ownerId = contract.ownerId) and sets contract.eventId + bumps contract.version in one transaction, returning {contract, event}.
  • Archiving: DELETE /api/v1/contracts/{id} sets archived = true (204); ?hard=true is allowed for admin only (403 for board).

Structure

Vertical slice flow:

Web /contractacions & /contractacions/{id}
  → ContractsViewModel → ContractsRepository → MuixerangaApi
  ↕ JSON over HTTPS (Bearer, board/admin only)
Server ContractRoutes → ContractService (+ EventService) → Contracts.sq (SQLite v0.2)

Summary metrics (GET /api/v1/contracts/summary?year=YYYY, non-archived contracts of that year):

  • confirmedIncome: sum of amount (MoneyCents) for status ∈ {confirmed, done, invoiced, paid}
  • openCount / openAmount: count & sum of amount for status ∈ {to_contact, contacted, proposal_sent, negotiating}
  • pendingPaymentAmount: sum of amount for status ∈ {done, invoiced}
  • overdueCount: count where overdue == true
  • dipuCatalog: {confirmed, limit, total}
  • byStatus: map of ContractStatus -> {count, amount}

Sections

Filters, sorting & pagination (§6.2 & §6.7)

Contents

GET /api/v1/contracts supports page, perPage, type, status (comma-separated list), ownerId, overdue (bool), archived (default false), year (matches performanceDate year or updatedAt year when performanceDate is null), q (case-insensitive search in title, client_name, client_municipality), and sort (updatedAt, performanceDate, nextActionAt, amount, title; default -updatedAt).

Behavior

Validate sort field names strictly against an allowlist (400 invalid_parameter on unknown fields); never concatenate user input into SQL.

Diputació limit confirmation & create-event flow

Contents

When the user creates, edits, or clicks → advance to set a dipu_catalog contract to confirmed (or later) and summary.dipuCatalog.confirmed >= summary.dipuCatalog.limit, the UI displays a confirmation dialog in Valencian before sending the mutation.

Behavior

When clicking «Crea l'esdeveniment al calendari», if contract.performanceDate != null, call POST /contracts/{id}/create-event directly; if null, open a modal requesting date (required) + optional endDate/allDay and submit them in the request body. On success, display the link to the newly created calendar event.
